# BeModel 项目功能分块与双人熟悉分工

## 1. 目的与分工原则

本文用于两名同事共同熟悉项目，按业务功能划分阅读范围，并约定需要共同理解的接口和流程。这是学习分工，不涉及拆分服务、调整数据库或重构代码。

- **同事 A：本体与数据底座。** 理解业务知识如何定义、映射、校验和发布，以及如何支持指标、治理和推演。
- **同事 B：AI 与业务应用。** 理解问题如何进入系统，如何调用模型、查询数据、检索知识，并形成回答、诊断和处置结果。
- 每人负责自己功能对应的前端页面、接口、后端服务、数据库结构及测试，跟完完整业务链路。
- 按功能分工，不直接按包划界；`ontology` 和 `cs` 包中的职责需要进一步区分。

下文中的后端包均位于 `bemodel-server/src/main/java/com/bemodel/`，前端页面位于 `bemodel-web/src/views/`。

## 3. 同事 A：本体与数据底座

### 3.1 推荐阅读顺序

1. **本体数据模型：** 阅读 `ontology` 的实体、Mapper 和核心服务，区分概念、属性、关系、术语、指标与物理表。
2. **数据源与映射：** 阅读 `datasource`、`instance`，跟踪数据源注册、扫描、映射确认和业务库查询流程。
3. **校验与发布：** 阅读 `modeling`、`rdf`，理解状态流转、评审权限、发布快照和 SHACL 校验。
4. **本体完善：** 阅读缺口、提案、漂移逻辑，理解未覆盖说法如何进入建模流程。
5. **指标与治理：** 阅读指标、巡检、对账和数据质量规则，明确查询、告警、工单分别写入哪些表。
6. **推演：** 阅读 `simulation`，理解本体关系和映射如何支撑影响链查询。

### 3.2 前端范围

主要阅读 `ontology`、`datasource`、`glossary`、`evolve`、`drift`、`gov`、`simulation` 页面及对应的 `src/api/` 接口封装。对于嵌入其他页面的指标和对账功能，继续跟踪对应接口，不仅按页面目录划界。

### 3.3 重点入口

| 入口 | 阅读重点 |
|---|---|
| `ontology/service/ConceptService.java` | 概念管理及其生命周期 |
| `datasource/service/DatasourceService.java` | 注册连接、密码处理、业务库 JDBC 获取 |
| `modeling/service/ReleaseService.java` | 发布流程、门禁与快照 |
| `ontology/service/OntologyCheckService.java` | 本体一致性检查 |
| `ontology/service/MetricService.java` | 指标口径与探针 |
| `ontology/service/ReconcileService.java` | 本体侧对账逻辑 |
| `cs/ReconciliationService.java` | 应用侧对账逻辑，与上一个服务对照阅读 |
| `simulation/SimulationService.java` | 变更施加、传导查询、前后观察和结果保存 |

### 3.4 应能讲清的问题

- 一个业务概念怎样对应到实际数据库中的表和字段？
- 哪些概念、关系与映射可以供应用使用，状态限制在哪里执行？
- 新增或修改本体后，怎样校验、评审和发布？
- 指标数字从哪里计算，巡检、告警和对账结果分别如何保存？
- 推演有哪些证据，遇到缺失映射时如何停止或标记？

建议完整跟踪一条链路：**定义概念与属性 → 注册并扫描数据源 → 确认映射 → 校验并发布 → 说明问数侧如何使用这些数据。**

## 4. 同事 B：AI 与业务应用

### 4.1 推荐阅读顺序

1. **LLM 网关：** 阅读 `llm`，确认请求格式、配置来源、超时、主备切换、审计和降级行为。
2. **智能问数：** 从 `CsController` 跟踪到 `CsService`、`SemanticQaService`，再跟到本体、映射、指标和数据库查询。
3. **知识库：** 阅读 `knowledge`，理解文档摄取、切分、检索及问答引用流程。
4. **客服与医疗应用：** 阅读客服诊断、`rca`、`flow`、`link`、`clinical`、`impact`，区分查询分析与业务写操作。
5. **证据与开放接口：** 阅读 `trace`、`mcp`，确认结论如何追溯、哪些能力可供外部调用。
6. **实验与评估：** 阅读 `lab`、`value`，理解沙箱、工具执行和对比结果。

### 4.2 前端范围

主要阅读 `ask`、`cs`、`knowledge`、`trace`、`flow`、`link`、`clinical`、`lab`、`value` 页面及对应的 `src/api/` 接口封装。

### 4.3 重点入口

| 入口 | 阅读重点 |
|---|---|
| `llm/DeepSeekClient.java` | 模型请求、响应解析、路由、熔断和降级 |
| `cs/CsController.java` | 客服与问答接口入口 |
| `cs/CsService.java` | 场景路由、客服诊断和回复编排 |
| `cs/SemanticQaService.java` | 语义问数、指标匹配、SQL 校验与执行 |
| `cs/ClarifyService.java` | 澄清任务推进 |
| `knowledge/KnowledgeSearchService.java` | 知识召回与混合检索 |
| `lab/LabSandboxService.java` | 实验沙箱创建、克隆与重置；与 A 共同理解 |

### 4.4 应能讲清的问题

- 一个问题如何进入客服、智能问数、指标或文档问答流程？
- 本体和映射如何进入模型上下文，生成的 SQL 怎样校验？
- 回答中的数字、引用和证据分别来自哪里？
- 模型不可用、没有映射或检索不到文档时如何处理？
- 客服处置会修改哪些数据，沙箱实验与演示业务库如何区分？

建议完整跟踪一条链路：**前端提问 → 场景路由 → 获取本体与映射 → 模型生成查询 → 校验并执行 → 生成回答 → 保存证据。**

## 5. 共同阅读与交接边界

### 5.1 共同起步

开始时共同阅读 `README.md`、`pom.xml`、`application.yml`、`application-dev.yml`、`BeModelApplication.java`，以及 `common`、`auth`、前端路由、请求封装与用户状态。

在约定的开发环境共同跑通登录、查看概念与映射、一次问答。需要运行集成测试或推演时，先确认目标数据库和写入范围；这些流程并非全部只读。

### 5.2 必须对齐的交接点

| 交接点 | A 需要说明 | B 需要说明 |
|---|---|---|
| 本体与映射 → 问数 | 数据结构、状态、映射与场景数据源范围 | 如何组装上下文、校验查询及处理零映射 |
| 指标 → 自然语言回答 | 指标定义、探针、实测值与巡检记录 | 如何匹配指标、调用探针、表达数字 |
| 应用反馈 → 本体完善 | 缺口、提案、术语与概念的治理流程 | 哪些问答或搜索结果触发缺口记录 |
| 对账 → 客服与证据 | 差异计算、认领、裁决及结果状态 | 应用怎样展示、引用或触发对账 |
| 推演 → 实验沙箱 | 推演修改哪些数据、怎样计算影响 | 沙箱克隆与重置机制；两个模块共享 `bemodel_lab` |
| 权限与审计 | 建模、评审、发布的权限边界 | 问答、处置、MCP 和模型审计的边界 |

特别注意：`cs` 中的对账由 A 主读，问答与客服由 B 主读；`ontology` 中的指标由 A 主读，B 需要理解消费方式。`simulation` 与 `lab` 共享实验库，推演会重置沙箱，应共同确认使用方式。

## 6. 阅读方法与阶段产出

每个功能按 **前端页面及 API → Controller → Service → Entity / Mapper → SQL 迁移 → 对应测试** 的顺序阅读。测试优先用于理解输入、输出、失败路径和业务约束，不要求一开始执行全部测试。

不必从 V1 开始顺读所有迁移，也不必先通读 `DataSeeder`；遇到表结构、演示关系或数据来源问题时，再定位相关脚本和初始化代码。

两人各自整理以下内容，作为交叉讲解材料：

1. 负责功能的页面和接口清单。
2. 一条完整调用链，说明关键类、查询和写入位置。
3. 核心表及其关系，不必覆盖所有辅助表。
4. 与另一人的接口、数据结构和状态约定。
5. 已确认的功能限制，以及仍需核实的问题。

完成初步阅读后，A 讲解“本体和映射如何向应用提供语义”，B 讲解“问数和业务应用如何使用这些语义”。双方共同复核 `SemanticQaService` 与本体、映射、指标服务的衔接，确保能够合起来解释端到端流程。
